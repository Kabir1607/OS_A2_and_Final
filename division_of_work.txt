SMART LIBRARY: DIVISION OF WORK (A1 port, A2, Final)
=====================================================

Interface contract: library_sim.pyi (repo root). Every function you
provide or call is specified there: inputs, outputs, errors and who owns
it. Code against it, not against someone's half-finished file. If you
need a signature changed, tell the group, then edit the .pyi.

Common rules (everyone)
- Python 3.10+, standard library only at runtime. Tests use `unittest`
  (they also run under pytest).
- One module per responsibility, as laid out at the top of the .pyi.
- Only the engine's coordinator thread touches Reader / ReadyQueue /
  SeatPool / AdmissionQueue. Worker threads only touch ResourceManager and
  Tracer. No sleep() for correctness, no busy-waiting.
- Same input + options => same output (except the order of racing trace events).
- Each owner writes unit tests for their own module plus their README section(s).
- Shared fakes: each owner publishes tests/fakes/fake_<module>.py and
  tests/contract/test_<module>_contract.py EARLY (see the .pyi header).
  Test against other people's published fakes, never against private ones.
- Read the "[CONTRACT 1-6]" rules in the .pyi that touch your module. They
  cover behaviour between modules that the formats alone don't pin down.
- Everyone must be able to explain the WHOLE system in the viva.

Samar: concurrency, synchronization, deadlock (Final core)
-----------------------------------------------------------------------
Modules: resource_parser.py, trace.py, resources.py, workers.py, deadlock.py
Depends on: Kabir's models/errors only, so you can start immediately.

S1. resource_parser.py: parse the R and K sections and validate_actions
    (declared/standard IDs, capacity 1, units 1, 0 <= offset <= SERVICE,
    per-reader replay: no release-without-hold, no double acquire, nothing
    held at the end). Clear InputError messages with line numbers.
S2. trace.py: thread-safe Tracer (lock + global seq), TraceEvent with
    thread name, format_event, audit_exclusivity (independent replay,
    also flags RELEASE/ROLLBACK by a non-holder). Follow the event-shape
    table in [CONTRACT 3]: one ROLLBACK event per book, and HANDOFF names
    the NEW holder, straight after the RELEASE/ROLLBACK.
S3. resources.py: ResourceManager with threading.Lock/Condition. Emit
    trace events INSIDE the lock [CONTRACT 3]. acquire() raises RuntimeError
    on a re-acquire by the holder or a waiter [CONTRACT 1]. Atomic
    check-and-update, FIFO waiters per resource, direct handoff on release
    (no lost wake-ups, no stealing), double-release detection, per-resource
    stats (max holders, acquisitions, wait events), exclusivity counter,
    wait_for_graph, nothing_held.
S4. Implement BOTH prevention policies inside ResourceManager, selectable
    per run (exact rules in the PreventionPolicy docstring in the .pyi):
    - ROLLBACK: breaks hold-and-wait. A reader that would wait while holding
      releases everything and waits for the whole set, granted atomically.
    - ORDERED: breaks circular wait. Global rank = sorted resource IDs. A
      reader may only WAIT for a resource ranked above all it holds. A free
      resource is granted in any order. An out-of-order wait releases only
      the higher-ranked held books, then re-acquires them in ascending order.
    Neither policy may reject an input because of its acquisition order.
    Also resource_rank() and the PolicyStats counters (policy_stats()).
S4b. Policy unit tests, the same suite run against both policies: in-order
    pair, reversed pair (circular), 3-reader cycle, out-of-order but
    uncontended acquire (ORDERED must NOT roll back), a reader needing 3
    books, rollback that wakes another reader, handoff chains. Assert
    held_while_waiting == 0 under ROLLBACK, and the ordered-wait invariant
    under ORDERED (checked inside the lock).
S5. workers.py: WorkerPool over real threads (ThreadPoolExecutor or
    threading.Thread + queue), run_batches returns results in order,
    re-raises worker exceptions, no sleep. Show >= 2 workers overlapping
    (thread names in the trace).
S5b. Overlap evidence (Final spec section 4.1): with tiny tasks, a thread pool
    may run two batches one after the other on the SAME thread, so the
    trace would show no overlap. Record real perf_counter start/end
    intervals per batch, make sure contending batches run on distinct
    threads (e.g. a Barrier before the critical section in a contention
    workload), and print an "overlap" line in the trace naming both
    threads. Stress tests use sys.setswitchinterval(1e-6) to force more
    thread switches (in tests only).
S6. deadlock.py: find_cycles, UNSAFE_DEMO_INPUT (inputs/deadlock_unsafe.txt,
    the spec workload with R2 reversed), and run_unsafe_demo, which runs
    the REAL engine once per policy [CONTRACT 5]. It is bounded because the
    engine stops when no progress is possible, so no timeouts are needed.
    NONE reports the cycle and UNRESOLVED_DEADLOCKS = 1. ROLLBACK and
    ORDERED both complete, and the trace shows how each broke the cycle.
    Build it against fake_engine until the real engine works.
S6b. Optional: run_blocking_demo (Barrier + Condition.wait(timeout)) with
    real thread blocking, using the SAME ResourceManager.
S6c. Publish fake_resources (with direct handoff and the [CONTRACT 3]
    trace events), fake_workers and their contract tests EARLY. The
    engine's correctness depends on the fake behaving like the real one.
S7. Concurrency tests + stress tests: many readers racing for the same
    book (holders never > 1), different copies in parallel (OS_BOOK_3 and
    OS_BOOK_7 held simultaneously), release -> wake-up, repeated
    acquisitions, equal-offset simultaneous requests, randomized workloads
    run many times checking invariants (0 violations, nothing held at end).
S8. Final input files: the spec workload, the reversed-order unsafe
    workload (must complete under both policies), a reader blocked while
    holding a book, and the interaction with memory blocking.
S8b. Policy comparison workloads (inputs/policy/*.txt). Each is designed to
    test ONE hypothesis below, and we keep whatever the numbers actually show:
    P1 in-order, low contention (spec workload). Expect a tie on metrics,
       ORDERED with 0 rollbacks vs ROLLBACK with some (less churn for ORDERED).
    P2 in-order, high contention, long holds. ROLLBACK frees books earlier,
       so others may wait less. ORDERED holds while waiting (convoy).
    P3 reversed order / circular (R1: REF->JOURNAL, R2: JOURNAL->REF, and a
       3-reader cycle). Both are safe. Compare rollbacks and resources_rolled_back.
    P4 out-of-order but uncontended. ORDERED does nothing extra.
       ROLLBACK does nothing either. Check that both have zero overhead.
    P5 multi-book reader vs a stream of single-book readers. ROLLBACK's
       all-or-nothing wait may starve it (max_resource_wait). ORDERED
       progresses step by step.
    P6 randomized stress (many readers, many copies, random orders), with
       wall_time_s as the synchronization-overhead measure.
S8c. With Aarush: run compare_policies on P1-P6 x {FCFS, PRIORITY},
    30 repeats. Write the "which policy wins where, and why" table, then
    pick DEFAULT_POLICY with a one-paragraph justification. Commit the
    choice in deadlock.py before Urvashi builds the Final zip.
S9. README: Coffman conditions in the Library, threading model + GIL note
    (concurrency, not parallelism, so locks are still needed), primitives
    used and why, ownership/waiting rules, BOTH prevention designs (which
    Coffman condition each breaks, and why each accepts any input order),
    the ROLLBACK vs ORDERED comparison table and the default-policy choice,
    limitations (no offset rewind, possible starvation under ROLLBACK,
    convoying under ORDERED), and the deadlock demo under NONE/ROLLBACK/ORDERED.
    Also justify: (a) why "returns BLOCKED + rescheduled by the coordinator"
    is the spec's "equivalent thread-safe event mechanism" (section 5.2)
    and how direct handoff prevents lost wake-ups and stranded waiters;
    (b) the fairness assumption (FIFO waiters per resource, no strict lock
    fairness); (c) why process-state transitions are race-free: confined to
    the coordinator thread (section 4.1); (d) the code never relies on the GIL
    for atomicity, so it would stay correct on a free-threaded build.
